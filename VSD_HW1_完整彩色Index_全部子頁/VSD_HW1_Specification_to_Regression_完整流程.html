VSD HW1｜完整設計與驗證流程

本頁完整展開附件中的流程：Specification → Encoding → RTL Datapath → TB Stimulus → Golden Compare → Waveform Debug → Lint → Regression。它不是八個互不相關的步驟，而是一個會反覆迭代的 RTL 開發閉環。以下直接連結到你的 HW1：ALU 31 個 operations，以及 FPU MIN / MAX / ADD / SUB。

Specification→Encoding→RTL Datapath→TB Stimulus→Golden Compare→Waveform Debug→Lint→Regression

真正完成的條件：不是「code 寫完」，而是 specification 已轉成 RTL，而且官方 patterns、邊界測試、handshake、lint 與完整 regression 都能一致驗證。

Specification｜先知道硬體「應該做什麼」

Specification 是所有後續工作的唯一出發點。此時不要急著寫 always_comb，先把 operation、I/O、特殊規則、位寬、signedness、timing 全部整理成可實作條件。

HW1 類別需要從規格抽出的內容若漏掉會怎樣
ALUinstruction_i、src_A_i、src_B_i、result_o；RV32IM/RV32B/DSP operationsdecode 或 arithmetic semantics 錯
DSP4× signed 8-bit lanes、per-lane saturation、ABS INT_MIN、CLIP8 sign extension一般 case 過、boundary fail
FPUIEEE-754 S/E/F、special values、alignment、normalization、GRS/RNE最後 bit、NaN/Inf/zero 等錯誤
Protocolenable / valid / clk / reset數學答案對但 TB hang/fail
讀題→列 I/O→列 Operations→列 Corner Cases→定義 Timing

Encoding｜把 32-bit instruction 轉成 operation

CPU 不會看到文字「ADD」或「SADD8」，RTL 收到的是 instruction_i[31:0]。所以必須先抽欄位，再分層 decode。

instruction[31:25]=funct7　|　[24:20]=rs2 field　|　[19:15]=rs1 field　|　[14:12]=funct3　|　[11:7]=rd　|　[6:0]=opcode
instruction_i→opcode→funct3→funct7 / [24:20]→operation select
logic [6:0] opcode = instruction_i[6:0];
logic [2:0] funct3 = instruction_i[14:12];
logic [6:0] funct7 = instruction_i[31:25];

例如 ADD 與 SUB 可以共享 opcode/funct3，但由 funct7 再區分。Custom DSP 則先命中 DSP opcode，再用 funct3 選 DOTP4/SADD8/SSUB8/ABS/CLIP8。

RTL Datapath｜把規格變成真正的硬體資料路徑

ALU Datapath

FPU Datapath

RTL 問題一定要明確決定
Signedness$signed 在哪裡需要？SLT/SLTU、MULH family、DSP lanes。
Intermediate width8-bit saturation 先擴 9-bit；32×32 multiplication 要保留完整 product。

Default assignmentalways_comb 要避免漏賦值形成 latch。

TB Stimulus｜Testbench 如何把測資送進 DUT？

CSV→$fopen→$fgets→$sscanf→Drive DUT

ALU

輸入 instruction/A/B 後等待一小段 simulation time，再讀 result_o。這是 combinational verification。

FPU

A/B/op+enable=1→ posedgeenable=0→wait valid→capture co

這一步驗證的不只是 arithmetic，也驗證 transaction timing。

Golden Compare｜GOT 與 EXP 必須怎麼比？

DUT Output = GOT↔CSV Answer = EXP→PASS / FAIL

HW1 的比較本質是 bit pattern verification。FPU starter TB 使用 bit-exact comparison，因此不是「小數差不多就算對」。GRS/RNE、signed zero、special-value pattern 都可能決定最後 32 bits。

若 FAIL先保存
ALUinstruction、A、B、GOT、EXP、operation ID
FPUline、A、B、instruction、GOT、EXP、valid timing

不要一次看 500 個 FAIL。第一個 failing vector 通常已足夠找到共同 root cause。

Waveform Debug｜找「第一個錯」而不是只看最後 output

FAIL Vector→定位 Wave 時間→Inputs→Decode/Classify→Intermediate→Output
ALU 波形FPU 波形
opcode / funct3 / funct7clk / rst / enable / valid
src_A / src_BS/E/F classification
signed compare / shamtexp_diff / aligned mantissa
product / DSP lanesG/R/S / raw sum-diff
result_onormalized / rounded / packed co
verdi -ssf ALU.fsdb &
verdi -ssf FPU.fsdb &

如果 output 錯，不代表 output mux 就是 root cause。真正要找的是訊號鏈上最早開始與預期不一致的位置。

Lint｜不用跑 Pattern 也能抓的 RTL 問題

jg -superlint superlint.tcl
Lint 問題HW1 典型例子修法方向
Width mismatch8-bit exponent 與 unsized 32-bit literal 混用使用明確 sized literal/cast
Signednesssigned DSP lane 被當 unsigned明確宣告/cast signed
Latchalways_comb 某 branch 沒賦值default assignment + 完整 branch
Unused/dead logic宣告 intermediate 卻未使用確認是否漏接 datapath
Multiple driver同一 reg/logic 多處賦值統一 ownership

不要把「關掉 warning」當作修好。先理解 warning 指向的語意問題，再修改 RTL，最後重跑 simulation。

Regression｜修一個 Bug 後，為什麼全部都要重跑？

因為修正某個 case 可能破壞原本已通過的 case。Regression 的目的就是確認「新修正沒有造成舊功能退化」。

Fix Root Cause→Recompile→Failing Case→Directed Boundary→Official ALU/FPU Patterns→Superlint→PASS

HW1 最後應同時具備：official regression、你自己的 corner/hidden-defense tests、lint 結果，以及能對應報告內容的 waveform/log evidence。

完整 Debug 閉環｜FAIL 後到底怎麼走？

Regression FAIL→保存第一筆 FAIL→建立最小 Reproducer→Verdi 找第一個錯訊號→定位 Root Cause→修 RTL→Lint→Full Regression
症狀優先方向
Compile 根本失敗syntax / include path / module / port
ALU 某一 family 全錯encoding/decode
只有 signed case 錯signedness / extension
DSP saturation boundary 錯intermediate width / per-lane clamp
FPU 差最後 1 bitGRS / RNE
FPU 卡住enable/valid handshake
Simulation PASS 但 lint warning 多RTL 結構仍需修正，不代表完成
