00-9｜Testbench / Handshake：enable / valid 如何配合 Clock？

本章直接以 VSD HW1 的 starter testbench 行為為核心。ALU 是 combinational 驗證；FPU 則有 clk / rst / enable / valid，所以除了「數學答案正確」之外，還必須符合 transaction timing。尤其 FPU TB 會送入 enable pulse，接著等待 valid，最後才讀取 co。

一、Testbench 到底在做什麼？

CSV Golden Pattern→TB 讀取一列→Drive DUT Inputs→等待 DUT 完成→Capture Output→Bit-exact Compare→PASS / FAIL

可以把它記成：CSV 是答案資料、TB 是監考老師、RTL 是考生、waveform 是監視器。

二、ALU TB：為什麼不需要 enable / valid？

HW1 ALU 介面只有 instruction_i / src_A_i / src_B_i → result_o。它是 combinational ALU，因此 TB 的概念是：

設定 instruction/A/B→等待 #10→讀 result_o→與 expected 比較

#10 在這裡是 TB 給 combinational logic 一段 simulation time 後再檢查，不是 ALU 內部「需要 10 ns 才完成」的硬體 handshake protocol。

三、FPU 為什麼需要 Handshake？

Signal方向角色
enableTB → FPU「這個 clock edge 有一筆新 request」
ai / biTB → FPUoperand data
instructionTB → FPUMIN/MAX/ADD/SUB
validFPU → TB「現在 co 是這筆 request 的有效答案」
coFPU → TB32-bit result
Request side：enable + input data　｜　Response side：valid + output data

因此 enable 和 valid 不是同一件事。enable 表示輸入被送進去；valid 表示輸出現在可以被讀。

四、Starter FPU TB 的實際 Timing

Starter TB 使用 forever #5 clk = ~clk;，所以 clock period 是 10 ns。send_and_check 的核心時序為：

time ────────► clk ___/‾‾‾\___/‾‾‾\___/‾‾‾\___/‾‾‾\___ ↑ ↑ ↑ edge 1 edge 2 later edge A/B/op ======= TRANSACTION N ================= enable ________/‾‾‾‾‾\________________________ ↑ DUT 接收 request valid ________________________/‾‾‾\___________ ↑ TB 才可讀 co co xxxxxxxxxxxxxxxxxxxxxxxx RESULT N ======= ↑ valid=1 時有效

TB 先把 start(enable)=1，等待一個 posedge，然後把 start 拉回 0；再至少等待下一個 posedge，之後以 while(!ready) 等待 valid。

五、逐 Clock 看一次 Transaction

階段TBDUT 應理解為
送資料設定 A/B/instruction，enable=1request 已準備好
posedge #1TB 等待 edge可在這個 edge latch request
edge 後enable=0不要把同一筆資料重複接收
posedge #2TB 再等一個 edge若尚未 valid，繼續計算
later edgeswhile(!valid)尚未完成就繼續等待
valid=1讀 coco 必須與這筆 transaction 對應

六、Latency 與 Throughput 不要混在一起

概念意思例子
Latency從 request 被接受到 result valid 經過多久3 cycles 後 valid
Throughput多久可以接受一筆新的 request每 cycle 1 筆 / 每 4 cycles 1 筆

Starter TB 是一筆一筆送：送完後等待 valid，再處理下一筆。因此你的第一優先是讓每筆 request 都能可靠完成，不需要自行假設 TB 會每 cycle pipeline 灌資料。

七、valid 最安全的思考方式

Idleenable=1 →Capture Input→Compute / Wait→Write co+valid=1→回 Idle

不論你設計是 1-cycle 或 multi-cycle，核心 invariant 都是：當 valid=1 時，co 必須已經是正確且穩定的該筆答案。

錯誤結果
valid 永遠 0TB 卡在 while(!ready)，simulation 不會前進到 compare。
valid 太早TB 讀到上一筆或尚未完成的 co。
valid 與 co 差一 cycle數學 datapath 可能正確，但 transaction 對不上。
enable 每 cycle 都當新 request同一筆可能重複啟動。

八、Reset 必須先看 TB 怎麼驅動

rst   = 1;
start = 0;
a     = '0;
b     = '0;
#20;
rst   = 0;

Starter TB 在 simulation 一開始令 rst=1，20 ns 後改成 0，因此這個介面預期的是 active-high reset 行為。Reset 期間至少要把 control state、valid 等初始化到已知狀態，避免一開始就出現 X 或假的 valid。

十、為什麼 FPU 是 Bit-exact Compare？

Starter TB 的 comparison function 使用 x === y。因此：

co[31:0]===expected[31:0]→完全相同才 PASS

這不是用 decimal 的「差小於 0.0001 就算對」。Sign、Exponent、Fraction，甚至 signed zero / NaN pattern 等，都可能影響 bit-exact 結果。這也是 GRS/RNE 為什麼重要。

十一、Pattern CSV 如何變成一筆 Transaction？

ALU

inst_id, inst_hex, a_hex, b_hex, exp_hex

FPU

a_hex, b_hex, exp_hex, instruction
$fopen→$fgets→$sscanf→send_and_check→DUT→Compare

因此 pattern 不是 RTL 的一部分，而是 verification stimulus + golden result。

十二、Starter FPU TB 兩個很重要的陷阱

陷阱 1：while(!ready) 沒有 transaction timeout

如果你的 FPU 永遠不拉 valid，TB 可以一直卡住。檔案後面的 #(10*MAX) 是 pattern loop 結束後的額外 simulation delay，不是 while loop 的 per-operation timeout。

陷阱 2：if(n_fail < 5) 包住 PASS/FAIL 計數

原 starter TB 在 fail 到 5 筆之後，後續 transaction 的 n_total 仍可能增加，但 n_pass 與 n_fail 都不再更新。因此不要把 summary 中最多 5 個 FAIL 誤認成「總共只有 5 筆錯」。Debug 應從第一個 failure 找 root cause，再 full regression。

十三、自己做 Defense TB 時建議加入 Timeout

int wait_cycles;
wait_cycles = 0;

while (!valid && wait_cycles < 100) begin
    @(posedge clk);
    wait_cycles++;
end

if (!valid) begin
    $display("[TIMEOUT] DUT never asserted valid");
    $finish;
end

這不是要求你修改官方 TB，而是自己建立 debug/hidden-defense testbench 時很有用。否則 handshake bug 會讓 simulation 看起來像「當機」。

十六、寫 FPU Control 時的實作規則

規則原因
Reset 時 valid=0避免 TB 誤認為已有有效答案。
只在接受 request 時 capture inputs避免 inputs 後續改變影響正在處理的 transaction。
co 與 valid 同步valid=1 的那一刻 co 必須正確。
明確定義 valid 是 pulse 或 held-high避免重複消費同一結果；本作業需配合 starter TB 行為。
先用單筆 directed transaction 測 timing比直接跑 2000 筆更容易看出 off-by-one。
再跑完整 official regression單筆成功不代表所有 transaction sequence 都正確。
