二、ModelSim 指令流程

cd → vlib work → vlog → vsim → run -all → $finish → quit -sim

1. cd E:/StudentID_HW1/Sim

切換 ModelSim 目前工作目錄到 HW1 的 Sim 資料夾。之後編譯檔案、建立 library 等操作都以此處為基準。

2. vlib work

建立名為 work 的 ModelSim library。Verilog/SystemVerilog 編譯完成後的設計單元通常會放在這個 library 中。

3. vlog -sv 檔名

vlog 是 ModelSim 的 Verilog compiler；-sv 表示以 SystemVerilog 語法編譯。例如 vlog -sv ALU_tb_iverilog.sv。

4. vsim work.tb_ALU / work.tb_fp32

vsim 載入準備模擬的 top-level testbench。work.tb_ALU 表示從 work library 載入 tb_ALU。

5. run -all

讓模擬持續執行，直到 testbench 遇到 $finish 或其他停止條件。

6. quit -sim

結束目前 simulation session，但不一定關閉整個 ModelSim。

9.1 ALU：正式指令

cd {E:/StudentID_HW1/StudentID_HW1_ModelSim_Formal/StudentID_HW1/Sim}

# 建立 / 對應 work library
vlib work

# 顯示完整波形範圍

① cd {.../Sim}
將 ModelSim 的目前工作目錄切換到正式作業的 Sim 資料夾。外層的大括號是 ModelSim/Tcl 常見的路徑寫法，尤其路徑若含空白時可避免被拆成多個參數。
② vlib work
建立 work library。ModelSim 不直接把編譯後的 module 當成一般檔案執行，而是先把設計單元編譯進 library。
③ vmap work work
把邏輯 library 名稱 work 對應到目前實體的 work 目錄。如此後續 vlog 編譯與 vsim 載入時，ModelSim 能正確找到 library。
④ vlog -sv ../Src/ALU.sv
以 SystemVerilog 模式編譯真正的 ALU RTL。../Src/ 表示從目前 Sim 資料夾往上一層，再進入 Src 資料夾。因此這次與先前把 DUT 包在單一測試檔中的方式不同，是明確地分開編譯 RTL 與 testbench。
⑤ vlog -sv ALU_tb.sv
編譯 ALU testbench。testbench 負責產生 instruction、輸入 operands、expected result，以及比對 DUT 的實際輸出。
⑥ vsim tb_ALU
啟動 tb_ALU top-level simulation。由 testbench 內部實例化 ALU DUT，因此載入 testbench 後，ALU 也會一起進入模擬。
⑦ view wave
開啟 ModelSim 的 Wave 視窗。這一步只負責顯示 waveform GUI，本身不會讓模擬時間前進。
⑧ add wave sim:/tb_ALU/*
將 tb_ALU scope 下的所有可見訊號加入 Wave 視窗。星號 * 是 wildcard，因此不用逐一輸入每個 signal 名稱。
⑨ run 200ns
讓模擬從目前時間向前執行 200 ns。這裡的目的不是一定要跑完整 testbench，而是先取得足夠的訊號變化來觀察 ALU 行為。
⑩ wave zoom full
自動縮放時間軸，使目前已經產生的全部 waveform 盡可能顯示在 Wave 視窗內，方便一次比較不同 instruction。

9.2 ALU Waveform 圖

圖 1　ALU 在 ModelSim Wave 視窗中的模擬波形。畫面可同時比較 instruction、src_A_i、src_B_i、result_o 與 expected result。

圖中左側可以看到 instruction_i、src_A_i、src_B_i、result_o、total_score、fail_count、inst_id、inst_hex、a_hex、b_hex 與 exp_hex 等訊號。這代表 testbench 不只把 DUT 的輸入輸出放到波形中，也保留了方便人工檢查的 instruction 編號與 expected value。

閱讀這張 ALU waveform 時，可以把每一段測試區間視為一筆測試案例：instruction_i 決定目前 ALU 要執行的運算，src_A_i 與 src_B_i 是兩個 operand，result_o 是 DUT 算出的結果，而 exp_hex 是 testbench 預期答案。人工驗證的核心就是檢查同一測試區間中的 result_o 是否與 expected value 一致。

畫面中的 inst_id 會依測試案例向後增加，可用來定位是哪一筆 instruction。這也解釋了為什麼 Transcript 最後可以逐項列出 Instruction 0 ALL PASS 到 Instruction 30 ALL PASS：testbench 正在系統化地對不同 instruction 與測試資料進行比對。

ALU waveform 判讀重點：不要只看綠色線條是否有變化；真正重要的是在同一測試時間區段內確認「instruction + A + B → result」的關係，並將 result_o 與 exp_hex 對照。前面的 Transcript 已顯示 Instruction 0～30 全部 PASS，因此 waveform 是進一步提供視覺化佐證。

9.3 FPU Waveform 圖

圖 2　FPU 在 ModelSim Wave 視窗中的模擬波形，可看到 clk、rst、start、a、b、result、ready、ins 與測試統計相關訊號。

FPU waveform 比 ALU 多了明顯的時序控制訊號。左側可看到 clk、rst、start、a、b、result、ready、ins、line_no、n_total、n_pass、n_fail、a_hex、b_hex、exp_hex 與 in 等訊號。

clk 持續週期性切換，表示 FPU 是由 clock 驅動的時序設計；rst 用來初始化設計；start 表示 testbench 發出新的運算要求；a 與 b 是輸入資料；result 是 FPU 計算結果；ready 則用來表示某筆運算結果何時有效。與純組合邏輯相比，FPU 的結果通常不能只看輸入改變的同一瞬間，而要配合 start、clock 與 ready 的時序關係來判讀。

圖中 ins 呈現 00、01、10、11 等不同控制值，代表 testbench 正在輪流測試不同 operation/control case。line_no 則依序增加，方便追蹤目前執行到第幾筆測試資料。a_hex、b_hex 與 exp_hex 則提供較容易人工比對的輸入與 expected result 表示方式。

因此 FPU 波形的正確閱讀順序可以整理成：先找到一個 start 啟動事件 → 確認當時的 ins、a、b → 等待 FPU 運算 → 在 ready 指示結果有效時讀取 result → 再與 testbench 的 expected result 比較。前面完整測試結果為 TOTAL=2000 PASS=2000 FAIL=0，因此所有 2000 筆比較均成功。
